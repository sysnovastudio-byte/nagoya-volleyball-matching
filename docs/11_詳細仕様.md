## 1. 技術・環境

| 番号 | 決定内容 |
|---|---|
| Q-01 技術構成 | 05の推奨構成を採用する（React、TypeScript、Vite、Tailwind CSS、shadcn/ui、Supabase、Playwright）。整形はPrettier、静的解析はESLint。独自のAPIサーバーは置かず、退会など秘密キーが必要な処理だけをSupabase Edge Functionsで行う |
| Q-02 公開環境 | Cloudflare Workers Static Assets。GitHubとの連携はWorkers Buildsを使う [2]。無料枠はビルド月3,000分、同時1件、20分で打ち切り [2] |
| Q-03 認証メール（一部） | カスタムSMTPを使い、**第一候補をResend**とする。無料枠は月3,000通・1日100通 [3]。利用者全員へ送るには**独自ドメインの検証が必要** [4] のため、Q-38（ドメイン）が決まるまで契約しない |
| Q-04 リージョン・環境分離 | 東京（`ap-northeast-1`）。開発用と本番用のプロジェクトを分ける。作成は許可を得てから行う |
| Q-05 無料枠・バックアップ | 公開まで無料プランとする。公開後は週1回と、DB変更の前に手動でバックアップし、リポジトリの外に暗号化して保管する。月1回、復元できることを確認する。使用量が上限の70%に達したとき、または一時停止を許容できなくなったときに有料化を検討する。予算の上限はQ-39 |
| Q-06 Node.js | 26系LTS。パッケージマネージャはnpm。両PCで同じバージョンに揃える |
| Q-07 リアルタイム通信 | **Broadcast（データベースから配信、非公開チャンネル）**。公式が拡張性と安全性の面で推奨し、Postgres ChangesのDELETEにはRLSが適用されない [5]。利用者からチャンネルへの送信は許可しない。実装前に小さな検証で確認する |
| Q-08 対応ブラウザ | Chrome・Edge・Safari・Firefoxの最新版と1つ前の版。下限はTailwind CSS v4の要件（Chrome 111、Safari 16.4、Firefox 128）。スマートフォンはiOSのSafariとAndroidのChrome |
| Q-09 自動テスト・自動公開 | GitHub Actionsで、プルリクエスト時に型検査・静的解析・単体テスト・ビルドを行う。Publicリポジトリでは標準ランナーを無料で使える [6]。`main` への反映後に公開する。プレビュー環境は本番DBにつながない。DBの変更は自動で適用せず、手動で行う |
| Q-48 Bot対策 | Supabase AuthのCAPTCHA保護をCloudflare Turnstileで有効にする。対象はログイン・登録・パスワード再設定 [1]。Turnstileの無料枠は20ウィジェットまで [7] |
| Q-49 認証の設定 | パスワードは10文字以上で、文字の種類は強制しない。漏えい済みパスワードの検査は有料プランの機能 [8] のため、有料化するときに有効にする。セッションはSupabaseの初期設定、認証・再設定メールのリンクは1時間有効 |
| Q-53 検索エンジン・SNS共有 | 初期リリースでは募集ページを検索エンジンに載せない（`noindex`）。共有はURLのコピーだけとし、OGPはサイト共通の画像・説明を使う。そのためSPAのままとする |

## 2. 募集・申請

### 2-1. 募集（Q-16・Q-17・Q-23・Q-24・Q-25・Q-46）

| 項目 | 決定内容 |
|---|---|
| 日時の上限 | 開催時間は24時間以内、開始は作成・編集の時点から1年以内（DB-04） |
| 追加する項目 | 終了日時（必須、開始より後）、対象レベル（必須、複数可）、説明（任意）、持ち物（任意） |
| 開催エリア | 名古屋市の16区から1つ選ぶ。区以外は選べないため、市外の募集は作成できない（Q-46）。住所の確認は通報と管理者の対応で補う |
| 公開する項目 | FR-05に加え、終了日時・対象レベル・説明・持ち物・残り枠数を未ログインにも公開する（Q-24） |
| 検索 | P0。日付の範囲、区、対象レベル、空きの有無で絞り込む（Q-23） |
| 一覧 | 開催開始前で、中止・非表示でない募集だけを、開催日時の順に表示する。締切済みは「受付終了」と示す |
| 状態 | 受付中（`open`）、締切（`closed`）、中止（`cancelled`）。「開催済み」は日時から判定する |
| 編集 | P0。開催開始前に主催者だけができる。定員は承認済み人数より少なくできない。日時・エリア・住所・参加費を変えた場合は、承認待ち・承認済みの人へ通知する |
| 締切 | P0。締切中は申請できないが、承認・却下・承認の取り消しはできる。受付を再開できる |
| 中止 | P0。開催開始前だけでき、元に戻せない。承認待ち・承認済みの人へ通知する。以後は申請・承認ができず、参加者は住所を見られない |
| 削除 | 主催者による削除は設けない（中止で対応） |
| 住所の閲覧 | 承認済みの参加者は、開催の終了日時まで閲覧できる。主催者は、終了・中止の後も閲覧できる（非表示の場合を除く。DB-07） |
| 終了・中止の後 | 主催者と参加者は「申請・募集の管理」で確認できる。一覧・検索には表示しない。詳細を見られるのは、主催者と、申請したことがある人だけ（DB-08） |
| 参加費 | アプリ内決済は行わない。当日の支払いを基本とし、方法は主催者が説明に書く。返金などの扱いはQ-31（Q-25） |

### 2-2. 申請（Q-14・Q-15・Q-26）

| 項目 | 決定内容 |
|---|---|
| 取り下げ | P0。承認待ちの本人が、開催開始時刻までできる。「取り下げ」（`retracted`）として記録し、主催者への通知は行わない。退会時に無効にする申請も同じ状態とする |
| 再申請 | 本人のキャンセル・取り下げの後はできる。却下・承認取り消しの後は、同じ募集に申請できない。同じ募集への申請は合計3回まで |
| 直前のキャンセル | 開催開始時刻までは制限しない |
| 無断欠席 | 初期リリースでは記録・表示しない |
| 履歴の公開範囲 | 本人と、その募集の主催者だけ。ほかの募集での履歴は主催者に見せない |

### 2-3. 申請の状態

| 状態 | 値 | 変わる条件 | 再申請 |
|---|---|---|:-:|
| 承認待ち | `pending` | 申請した | － |
| 承認済み | `approved` | 主催者が承認した | － |
| 却下 | `rejected` | 主催者が却下した | × |
| キャンセル | `cancelled` | 本人がキャンセルした。退会・利用停止にともなう場合を含む | ○ |
| 承認取り消し | `revoked` | 主催者が承認を取り消した | × |
| 取り下げ | `retracted` | 本人が取り下げた。退会・利用停止にともなう場合を含む | ○ |

## 3. チャット・通知・プロフィール

### 3-1. チャット（Q-10・Q-20・Q-21）

| 項目 | 決定内容 |
|---|---|
| 会話の単位 | 募集ごと、問い合わせユーザーごとに1つ |
| 開始できる人 | 問い合わせユーザー。主催者は、自分の募集に承認待ち・承認済みの申請がある人に対してだけ開始できる |
| 開始できる期限 | 申請前の質問は開催開始まで（中止・非表示では不可）。主催者と承認済みの参加者は、送信できる期間内（非表示では不可）（DB-10） |
| 会話一覧での表示 | 募集のタイトルと開催日時。非表示の場合は開催日時だけ |
| 編集・削除 | 設けない。管理者による非表示だけを行う（Q-51） |
| 送信できる期間 | 開催の終了日時から7日後まで。中止の場合も、予定していた終了日時から7日後まで。閲覧はその後もできる |
| 送信回数 | 利用者ごとに、1分間に10通、1時間に60通まで |
| 新しい会話 | 利用者ごとに1日（直近24時間、DB-05）10件まで |
| 相手が利用停止中・退会済み | 送信できない |

ブロックの影響：

| 対象 | 影響 |
|---|---|
| メッセージ | 双方向に送信できない【合意済み】 |
| 新しい参加申請 | 双方向に申請できない |
| すでにある申請・参加 | 変わらない。主催者は却下・承認の取り消しができる |
| 募集・プロフィールの閲覧 | 変わらない |
| 過去の会話 | 閲覧できる |
| 拒否の表示 | 「送信できません」「申請できません」とだけ示し、ブロックされたことは示さない |
| 解除 | P0。ブロックした相手の一覧から、本人が解除できる |

### 3-2. 通知（Q-11・Q-12）

初期リリースは**アプリ内の通知だけ**とする。メール・プッシュ通知は将来の候補（CND-13）。

| 出来事 | 受け取る人 | 機能ID |
|---|---|---|
| 参加申請 | 主催者 | NTF-01 |
| キャンセル（退会・利用停止にともなう場合を含む） | 主催者 | NTF-02 |
| 承認の取り消し | 参加者 | NTF-03 |
| 承認・却下 | 申請者 | CND-04 |
| 募集の日時・エリア・住所・参加費の変更、中止、管理者による非表示とその取り消し | 承認待ち・承認済みの人。非表示と取り消しの場合は主催者にも | NTF-04 |
| 新着メッセージ | P1。初期リリースでは通知しない | CND-05 |

- 通知の文面に住所・メールアドレス・停止の理由を含めない
- 退会・利用停止にともなう取り下げは、通常の取り下げと同じく主催者へ通知しない
- 作成から90日で削除する（DB-02）
- 非表示の取り消しは、開催開始前で中止されていない募集に限り知らせる（DB-16）

## 4. 安全対策・管理

### 4-1. 管理者（Q-28）

| 項目 | 決定内容 |
|---|---|
| 権限の付与 | 運営者がDBの管理操作で付与・剥奪する。画面からは変更できない。管理用のアカウントは、個人の利用とは分ける |
| 人数 | 初期は1人。公開前に、機器の紛失や不在に備えた復旧手順を文書にして試す。公開後に2人目を検討する（DB-15） |
| 一般ユーザーの操作 | 管理用のアカウントでは、申請・募集作成・メッセージ送信などを行わない |
| 画面への入口 | 管理者でログインした場合だけ、設定画面に入口を表示する |
| 多要素認証 | 管理者には必須とする。TOTP（認証アプリ）を使う方針とし、管理用関数が多要素認証済みのセッション（`aal2`）を確認する。動作は実装時に検証する【未確認】 |
| メッセージの閲覧 | 通報されたメッセージと、同じ会話の前後10件ずつ。閲覧できるのは通報が「対応中」の間だけとし、それ以外は通報時の控え（4-3）だけを見られる。終わった通報は、理由を記録して対応中に戻せる（DB-09） |
| 募集の閲覧 | 公開項目だけ。通報の確認などのため、終了・中止・非表示の募集も見られる |
| 操作の記録 | 管理者の閲覧・操作を記録し、1年で削除する。運営者がDBの管理操作で確認する（DB-12） |
| プロフィール | 通報された人の、ログイン済みに公開する項目だけ。年代・性別・活動地域、年齢の区分は見られない |
| 見られない情報 | 詳細住所（終了・非表示の募集を含む）、参加者の一覧、メールアドレス、ブロックの情報 |
| 利用者の探し方 | 通報から移動する、またはニックネームで検索する |
| 過去の措置 | 対象の利用者への措置の履歴を見られる |
| 新しい通報 | 通報管理に未対応の件数を表示し、1日1回以上確認する運用とする |

### 4-2. 利用停止（Q-28）

| 項目 | 決定内容 |
|---|---|
| 条件 | 規約違反や安全上の問題があると管理者が判断した場合。理由の分類（4-3と同じ）と補足を必ず記録する |
| 期間 | 期限を設けず、管理者が解除するまで |
| 解除 | 管理者が理由を記録して解除する。停止で取り消された参加・募集の締切は、自動では戻さない |
| 停止中にできること | 公開情報の閲覧（未ログインと同じ範囲）、ログアウト、退会 |
| 停止中にできないこと | 申請・承認・募集作成・編集・メッセージ・通報・ブロック・プロフィール編集、住所・会話・ほかの人のプロフィールの閲覧 |
| 停止された人の参加・申請 | 開催開始前のものを自動でキャンセル・取り下げとし、参加のキャンセルは主催者へ通知する（理由は示さない） |
| 停止された主催者の募集 | 管理者が停止と同時に、開催開始前の募集をまとめて「締め切る」か「中止する」かを選ぶ。中止した場合は、承認待ち・承認済みの人へ通知する（停止のことは示さない）。中止は解除しても戻せない（DB-13）。危険な場合は管理者が非表示にする（4-4） |
| 本人への表示 | ログイン時に、利用停止中であることと問い合わせ先（Q-32）を示す |
| 管理者の停止 | 画面から管理者を停止することはできない |

### 4-3. 通報（Q-29）

| 項目 | 決定内容 |
|---|---|
| 理由 | 迷惑行為・嫌がらせ／勧誘・宣伝／虚偽の内容／出会い目的／危険・違法な内容／個人情報の掲載／その他 |
| 状態 | 未対応（`open`）、対応中（`in_progress`）、対応済み（`resolved`）、対応不要（`dismissed`） |
| 証跡 | 通報時に、対象の内容（メッセージ本文、募集のタイトル・説明、ニックネーム・自己紹介）の控えをDB側で保存する。住所は含めない |
| 重複 | 同じ人が同じ対象に、対応が終わっていない通報を重ねることはできない |
| 自分への通報 | 自分自身・自分の募集・自分のメッセージは通報できない |
| 通報者による確認 | 確認する画面は設けない。受付完了だけを示す |
| 手順 | 確認 → 対応不要、または非表示・利用停止 → 状態と理由を記録。通報者の情報を相手に伝えない |
| 緊急時 | 通報画面に、身の危険がある場合は110番に連絡するよう案内する |
| 保存期間 | 対応が終わってから1年を初期値とし、控え・補足・対応の記録を消す（4-8。Q-32で確定） |

### 4-4. 非表示（Q-51）

- P0。管理者は、募集・メッセージを非表示にし、プロフィール画像を削除できる。どちらも理由を記録する
- 誤って非表示にした募集・メッセージは、管理者が理由を記録して戻せる（DB-06）。画像の削除は戻せない
- 非表示にした内容は物理的に削除せず、一般ユーザーには見せない。非表示の間、募集は中止と同じように申請・承認・住所の閲覧などができず、参加者と主催者へ通知する
- 非表示の募集は、主催者と申請したことがある人に「非表示になった募集」と開催日時だけを示す。主催者も住所を含めて閲覧・編集できない（DB-07）
- 画像は削除する。通報の控えには画像を含めない

### 4-5. 操作回数の制限（Q-47）

利用者ごとに次を上限とし、DB側で強制する。「1日」は直近24時間とする（DB-05）。登録・ログインはSupabase Authの制限（05の3-3）とQ-48で対応する。

| 操作 | 上限 |
|---|---|
| 募集の作成 | 1日5件 |
| 参加申請 | 1日20件 |
| 通報 | 1日10件 |
| ブロック | 1日50件 |

### 4-6. 障害・情報漏えい（Q-54・Q-55）

| 項目 | 決定内容 |
|---|---|
| 障害の告知 | アプリ上部にお知らせを表示する。アプリが使えない場合の告知先は、Q-38・Q-32と合わせて決める |
| 復旧 | 公開前に、バックアップからの復元手順を文書にして試す |
| 情報漏えい | ①被害の拡大を止める（公開停止・鍵の無効化）②範囲を調べる ③時系列を記録する ④本人への連絡と必要な報告を行う ⑤再発を防ぐ。報告の要否・期限は専門家に確認する（Q-33） |

### 4-7. 収益化・アクセス解析（Q-56・Q-57）

- 初期リリースでは、広告・課金などの収益化を行わない
- 初期リリースでは、アクセス解析ツールを入れない。CloudflareとSupabaseの標準の統計だけを見る

### 4-8. 保存期間（DB-01・02・11・12・14）

いずれも初期値で、Q-32で確定する。法的な対応で長く残す場合の扱いはQ-33〜Q-35。

| 情報 | 期間 |
|---|---|
| 通知 | 作成から90日 |
| 通報の控え・補足・対応の記録 | 対応が終わってから1年 |
| 措置の補足 | 対象者の退会から1年 |
| 管理者の閲覧・操作の記録 | 1年 |
| メール未認証のアカウント | 登録から30日 |
| 主催した募集の住所 | 主催者の退会まで |
| 再登録防止のハッシュ | 【未決定】Q-32 |

## 5. 画面に関する決定（Q-45の一部）

10の画面の分け方・遷移を採用する。各画面のレイアウトは【未決定】Q-45。

| 番号 | 決定 |
|---|---|
| 追加-01〜03 | ホームは募集一覧と統合、募集の作成と編集は共通、通知詳細は設けない |
| 追加-04 | 主催した募集の一覧（EVT-06）をSCR-009に置く |
| 追加-05 | 通報はSCR-019、ブロックはSCR-011・013。相手のプロフィールからも操作できる |
| 追加-06 | 認証メールの再送（AUTH-05）をSCR-003に置く |
| 追加-07 | 設定画面（SCR-015）を設け、ログアウトを置く |
| 追加-08 | ページがない・権限がない・利用停止中・通信エラーの案内は、共通の表示として用意する |
| 追加-09 | 申請はSCR-006、キャンセルはSCR-006・009。操作後は同じ画面に結果を示す。通報後は元の画面に戻る |
| 追加-10 | ログイン・登録・プロフィール入力の後は、元の画面に戻る |
| 追加-11 | 問い合わせ先は規約等の画面に示す（内容はQ-32）。使い方の専用画面は設けない |
| 追加-12 | ログイン後は、ホーム・申請と募集の管理・会話・通知・プロフィールへ、どの画面からも移動できるようにする |
| 追加-13 | 管理者は通報管理の未対応件数で気付く（4-1） |
| 追加-14 | ブロックした相手の確認（SAFE-08）をSCR-020に置く |
| 追加-15 | 通報者が自分の通報を確認する画面は設けない |
| 追加-16 | 管理者向け画面の入口は設定画面。管理用アカウントでは一般の操作を行わない（4-1） |
