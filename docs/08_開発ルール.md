# 08 開発ルール

表記ルールは [01_企画概要](01_企画概要.md) を参照。

本書は1人開発を前提とした運用案【提案】。「秘密情報の禁止」「合意済み仕様を独断で変更しない」は**必須**。

## 1. ブランチ運用

| ブランチ | 用途 |
|---|---|
| `main` | 動作確認済みの状態を保つ |
| `feat/<機能ID>-<内容>` | 機能追加。例：`feat/EVT-01-create-event` |
| `fix/<内容>` | 不具合修正 |
| `docs/<内容>` | 資料 |
| `chore/<内容>` | 設定・依存関係など |

- 実装開始後は `main` へ直接コミットせず、プルリクエストを通す（初回コミットは例外）
- 1つのブランチでは1つの目的だけを扱い、終わったら削除する
- ブランチ保護の設定可否は確認のうえ検討する。設定の有無によらず本ルールを守る
- `main` への強制Pushをしない

## 2. コミットルール

形式：`<種類>: <内容>`

| 種類 | 用途 |
|---|---|
| `feat` | 機能追加 |
| `fix` | 不具合修正 |
| `docs` | 資料 |
| `refactor` | 動作を変えない整理 |
| `test` | テスト |
| `chore` | 設定・依存関係 |

- 例：`feat: 募集作成フォームを追加 (EVT-01)`
- 1コミット1目的。日本語でよい
- 仕様変更は、コードと資料を同じプルリクエストで更新する

## 3. コーディング規約

- TypeScriptの `strict` を有効にし、`any` は原則使わない
- 入力は画面で検証し、DBでも必ず検証する
- DBアクセスを画面部品に直接書かず、機能ごとの処理にまとめる
- HTMLを直接挿入する機能（`dangerouslySetInnerHTML`）は使わない
- エラー画面やログに個人情報・内部情報を出さない
- 整形はPrettier、静的解析はESLintを使う（Q-01）。プルリクエスト時にGitHub Actionsで検査する（Q-09）

## 4. 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| Reactコンポーネント | PascalCase | `EventCard.tsx` |
| フック | `use` + PascalCase | `useEvents.ts` |
| 変数・関数 | camelCase | `remainingSlots` |
| 定数 | UPPER_SNAKE_CASE | `MAX_LENGTH` |
| フォルダ | kebab-case | `event-detail` |
| DBテーブル | snake_case・複数形 | `event_participants` |
| DBカラム | snake_case | `starts_at` |
| 環境変数 | UPPER_SNAKE_CASE | `VITE_SUPABASE_URL` |

shadcn/uiが生成するファイルは、生成時の名前に従う。

## 5. テスト方針

| 種類 | 対象 | 優先 |
|---|---|:-:|
| DB・RLS | 住所の公開範囲、定員、重複、ブロック、権限、送信回数 | 高 |
| ブラウザ（Playwright） | 登録、募集作成、申請、承認、キャンセル、チャット | 高 |
| 単体 | 入力検証、計算、表示の変換 | 中 |

- **許可されること**だけでなく、**拒否されること**もテストする
- 定員と重複は同時実行でも確認する
- テストデータは架空のものだけを使う
- 実行していないテスト、失敗したテストを「成功」と報告しない

## 6. Claude Codeへの作業依頼ルール

### 依頼に含めること

- 目的と対象の機能ID
- 読むべき資料
- 変更してよい範囲と、してはいけないこと
- 完了条件と確認方法

### Claude Codeが守ること

1. 作業前に関連資料と `git status` を確認する
2. 【合意済み】仕様を独断で変更しない
3. 【未決定】事項を独断で確定せず、確認する
4. 確認できない情報は「未確認」とする
5. 既存ファイルを確認せずに上書きしない。別プロジェクトに触れない
6. 外部サービスの作成、APIキーの発行、契約、本番DBの変更は、明示的な許可なしに行わない
7. 秘密情報を表示・保存・コミットしない
8. 実施したこと、していないこと、失敗したことを区別して報告する

### 依頼例

```text
docs/03、04、06を読み、APP-03（承認）を実装してください。
- 変更範囲：supabase/migrations と該当画面のみ
- 禁止：未決定事項の確定、本番環境の操作
- 完了条件：同時承認でも定員を超えないことをテストで確認
- 完了後：変更ファイル、テスト結果、残課題を報告
```

## 7. GitHubへのPushルール

Push前に確認する。

```powershell
git status
git diff --cached --stat
git diff --cached
git log --oneline "@{upstream}..HEAD"
```

初回Push前は上流ブランチがないため、最後のコマンドの代わりに `git log --oneline` を使う。

- [ ] 意図しないファイルが含まれていない
- [ ] `.env`、キー、パスワード、トークンが含まれていない
- [ ] 個人情報やDBのダンプが含まれていない
- [ ] 資料とコードが矛盾していない
- [ ] **Publicリポジトリで誰に見られてもよい内容だけである**（Issue・プルリクエスト・コミット履歴・作者メールを含む）

## 8. 環境変数・秘密情報の取り扱い（必須）

次の情報はGitHub、資料、Issue、スクリーンショット、チャットに載せない。

- `.env`、APIキー、パスワード、アクセストークン
- Supabaseのシークレットキー（`sb_secret_...`、旧 `service_role`）、DB接続文字列
- SMTPの認証情報
- 利用者の個人情報

誤ってコミット・Pushした場合：

1. **該当のキーやパスワードを直ちに無効化・再発行する**（履歴から消すだけでは不十分）
2. 影響範囲と不正利用の有無を確認する
3. 必要に応じて履歴から除去する
4. 原因と再発防止を記録する

## 9. 2台のPCでの開発ルール

2台のPCを、どちらも開発用として使う（Q-37）。会社PC・自宅PCという区別はしない。

### 9-1. 作業と同期

- どちらのPCでも、設計、ソースコードの作成・編集・修正を行える
- コードの同期はGitHubで行う。PCを切り替える前に、作業内容をコミットしてPushする（途中の場合は、作業ブランチに途中の内容としてコミットする）
- 別のPCでは、`git status` で未コミットの変更がないことを確認し、`git pull --ff-only` で最新にしてから作業する
- 同じファイル・同じブランチを2台で同時に編集しない
- Claude Codeは、指示がない限りコミット・Pushをしない。PCを切り替える前に、コミット・Pushを依頼する

### 9-2. 共有するもの・しないもの

| 区分 | 対象 |
|---|---|
| Gitで管理する | ソースコード、資料、設定ファイル、`package.json`、`package-lock.json`、変数名だけの `.env.example` |
| Gitで共有しない | `node_modules`、`.env.local` などの環境変数、秘密情報、ローカルDB、ビルド結果、テストの出力 |

- `package-lock.json` は手で作らず、npmで作る。最初に作ったPCからコミットする
- 2台のNode.jsなどのバージョンを揃え、[05](05_技術構成・開発環境.md) に記録する

### 9-3. 実行環境がないPCでの作業

- Node.jsなどがないPCでも、ソースコードの作成・編集を進めてよい
- 実行・ビルド・型検査・テストができない場合は、**できなかったことを明記する**。実施していないテストを成功と報告しない
- 実行できるPCで、型検査・静的解析・テスト・ビルドを通してから `main` に反映する
- ソフトウェアは、そのPCで許可された範囲で導入する。導入できないPCで、制限を避ける方法は使わない

### 9-4. 情報の取り扱い

- 勤務先など、本プロジェクトと関係のないデータ・アカウント・メールアドレスを使わない
- 本番の秘密情報や利用者の個人情報は、必要のないPCに置かない
- コミット前に `git config user.name` と `git config user.email` を確認する。作者情報は公開されるため、メールはGitHubのnoreplyアドレスを使う（PCごとにリポジトリ単位で設定）
- 離席時は画面をロックし、共用PCに認証情報を残さない
