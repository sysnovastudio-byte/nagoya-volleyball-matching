## 1. 重要な確認結果

| No. | 確認結果 | 影響 |
|---|---|---|
| 1 | Supabaseの標準メール送信は**1時間に2通**で、**プロジェクトのチームメンバー以外には送れない** [4] | メール認証を一般利用者に提供するには**カスタムSMTPが必要**。費用・送信元ドメインの検討が必要（Q-03） |
| 2 | Supabase無料プランは**1週間利用がないと一時停止**される [1] | 公開後も利用が少ないと停止し得る（Q-05） |
| 3 | Supabase無料プランに**自動バックアップは含まれない** [1][6] | 手段を自分で用意する（Q-05） |
| 4 | Cloudflareは公式ブログで、新規は**Workersから始めるべき**とし、Pagesはサポートを続けるが**今後の投資はWorkersに集中**するとしている [13] | Cloudflare PagesとWorkers Static Assetsを比較して決める（Q-02） |
| 5 | Supabaseは従来の `anon`・`service_role` キーを**2026年末までに廃止予定** [8] | 最初から新しいpublishable / secretキーで設計する |
| 6 | GitHub公式のプラン説明では、プライベートリポジトリのProtected branchesはPro・Teamの機能として記載され、Freeには記載がない [17] | 本リポジトリはPublicのため使える見込みだが、設定時に確認する【未確認】。設定の有無によらず運用ルールも守る（[08](08_開発ルール.md)） |

### 3-2. 無料枠を超えた場合

- 無料プランの上限を超え続けるとサービス制限が適用され、一時停止・読み取り専用・全APIの `402` 応答などになり得る [9]
- 適用前に猶予期間がある [9]。期間の長さは【未確認】
- 500MBの枠を超えただけでは読み取り専用にならない。読み取り専用になるのは**ディスク使用率95%**で、無料プランのディスクは2GB固定 [3]
- 枠の判定は組織単位 [3][9]

### 3-3. 認証・メールの制限

| 項目 | 制限 |
|---|---|
| 標準メール送信 | 1時間2通、チームメンバーのアドレスのみ、SLAなし（本番用途ではない）[4] |
| カスタムSMTP設定直後 | 1時間30通（変更可能）[4] |
| 確認メール・再設定メールの再送 | ユーザーごとに60秒の間隔 [4a] |
| 登録・ログイン | IPごとに5分30回（初期値）[4a] |

会社や施設のように複数人が同じIPを使う場合、IP単位の制限に注意する。SMTPサービスはResendとし、独自ドメインを取得してから契約する（Q-03、Q-38）。

### 3-4. その他

- 東京リージョン `ap-northeast-1` を選べる [11]。採用は東京（Q-04）
- `sb_publishable_...` はブラウザで使用でき、`sb_secret_...` はバックエンド専用 [8]
- シークレットキー（サービスキー）はRLSを迂回する [12]
- Postgres ChangesはRLSに基づき、閲覧できるクライアントにだけ届く [12a]。**DELETEにはRLSが適用されない**という情報があるが検索結果の要約で公式の記載を確認した（11のQ-07）。採用するBroadcastでは影響を受けない

## 6. 有料化の可能性【提案】

次の場合に有料化や構成変更を検討する。判断基準は11のQ-05。

- 一時停止を許容できなくなったとき
- 自動バックアップが必要になったとき
- DB、転送量、ファイル保存、Realtimeが上限に近づいたとき
- メール送信・独自ドメインに費用がかかるとき（構成によっては**公開前から発生し得る**）

### 7-3. セットアップ手順

ソフトウェアの導入と実装は自宅PCで行い、会社PCには導入しない（Q-37、11の7-5）。

1. Gitを確認：`git --version`
2. GitHub CLIを導入し、新しいターミナルで確認

   ```powershell
   winget install --id GitHub.cli --exact --source winget
   gh --version
   ```

3. GitHubへログイン（ブラウザの案内に従う。トークンを画面や資料に貼り付けない）

   ```powershell
   gh auth login --hostname github.com --git-protocol https --web
   gh auth status
   ```

4. リポジトリを取得（リポジトリ作成後）

   ```powershell
   gh repo clone <GitHubアカウント>/nagoya-volleyball-matching
   ```

5. 実装開始時：Node.jsの採用バージョン決定後に導入し、`node -v` と `npm -v` を両方のPCで記録する

## 8. 環境変数の管理方法【提案】

| 変数名（案） | 用途 | ブラウザに含まれるか |
|---|---|---|
| `VITE_SUPABASE_URL` | SupabaseのURL | 含まれる（公開前提） |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | publishableキー | 含まれる（公開前提。保護はRLSで行う） |

- `VITE_` で始まる変数はブラウザに配信されるコードに含まれる。**秘密情報に `VITE_` を付けない**
- シークレットキー、DBパスワード、SMTPのパスワードはフロントエンドに置かない
- 値は各PCの `.env.local` と、公開環境の環境変数設定で管理する
- `.env` 系は `.gitignore` の対象。変数名だけの `.env.example` は実装開始時に作成する
- PC間の値の受け渡しには、Git・メール・チャットを使わず、パスワード管理ツールなどを使う

## 9. 開発PC間の同期方法【提案】

1. 作業前に `git status` を確認し、`git pull --ff-only`
2. 作業後はコミットしてPush（途中ならブランチ上の作業中コミット）
3. 別のPCではPullしてから始める

- OneDriveなどの同期フォルダにリポジトリを置かない
- `node_modules` と `.env.local` は同期せず、PCごとに用意する
- 改行コードは `.gitattributes` でLFに統一する
