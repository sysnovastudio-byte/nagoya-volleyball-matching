# 04 機能一覧

表記ルールは [01_企画概要](01_企画概要.md)、要件番号（FR-xx）は [03_要件定義書](03_要件定義書.md) を参照。

> - 開発方針は**MVP優先のアジャイル開発**【合意済み】。プロトタイプ・限定公開MVP・将来追加の3段階に分ける（5-4）。「初期リリース」がどの段階を指すかは未確認（09のR-01）。
> - **機能ごとの分類（52件・21画面）とM-01〜M-14は、Claude Codeの提案で未承認**（11章）。承認されるまで、合意済み・決定済みの仕様を変えない。例外として、**M-04（検索は日付の範囲と区）と、M-01のうち年代をMVPに含めることは承認済み**【2026-11-26 ユーザーの決定】。
> - 2・3章の操作・処理・完了条件は、決定の記録がある仕様を示す。DB-17〜DB-30（06の11-1、未承認）は反映していない。

## 1. 分類

| 実装段階 | 分類 | 意味 |
|---|---|---|
| P0 | MVP必須 | 初期リリースに必須 |
| P0（一部・案） | MVP必須 | 範囲を狭めて初期リリースに含める案（6-2、未承認）。承認されるまではP0 |
| P1（案） | 公開後に追加 | 初期リリース後に追加する案（未承認）。承認されるまではP0 |
| P1 | 公開後に追加 | 初期リリース後に追加 |
| P2 | 現時点では不要 | 利用状況を見て判断する |

優先順位（高・中・低）は、同じ実装段階の中での着手順の目安【提案】。**「低」でもP0は初期リリースから外さない。**

「（仮）」が付いた実装段階は、採否が決まっていない。

## 5. MVPの方針

MVP優先のアジャイル開発に変更した【合意済み】（ユーザーの決定）。MVPを限定公開MVPとし、初期リリースと同じとみなすかは確認する（09のR-01）。5-1の優先する流れと、安全対策・個人情報保護・不正利用対策を省略しないことは、決定した方針である。5-2以降の分類、6〜11章は**【提案】で未承認**。

### 5-1. 優先する流れ

「募集を探す → 詳細を見る → 参加申請する → 主催者と連絡する」を完了できること。そのために必要な主催者側の操作（募集の作成、承認・却下）を含む。

| 段階 | 参加者側 | 主催者側 |
|---|---|---|
| 準備 | AUTH-01〜05、CND-01・09、PROF-01 | 同じ。EVT-01 |
| 探す | EVT-02、EVT-05 | － |
| 見る | EVT-03、APP-10 | EVT-06 |
| 申請する | APP-01・05・06・07、CND-04・10 | APP-02〜04、NTF-01、PROF-03 |
| 連絡する | MSG-01〜03、CND-05（未読の表示） | MSG-02・03・06、CND-05（同） |
| 参加する | EVT-04 | EVT-04 |
| やめる・断る | APP-08・09、CND-08 | APP-11、CND-03、NTF-02〜04 |
| 安全 | MSG-04・05、SAFE-01〜04・09・10、CND-06 | 同じ。運営はSAFE-05〜07、CND-07 |

### 5-2. 分類の基準

| 分類 | 基準 |
|---|---|
| MVP必須（P0） | 上の流れが途切れる、または、安全対策・個人情報保護・不正利用対策が欠ける |
| MVP必須の一部（P0（一部・案）） | 機能は必要だが、範囲を狭めても上の流れと安全が保てる |

- `P0（一部・案）` の完了条件は、2章の表ではなく6-2の「MVPに含める範囲」で読む
- 合意済み・決定済みの仕様を狭めるものは、11章のM-xxとして確認する。**承認されない場合は、元の仕様のまま限定公開までに作る**（9-4）
- 外した機能の仕様は取り消さない。2章と06・11に残し、追加するときに使う

| 申請の履歴の専用の表 | 操作者と原因が残らない | 運営者が経緯を調べる材料が減る。利用者は申請の行を直接変更できない | M-14。停止による取り消しかどうかは、措置の記録の日時と照らし合わせる |

| 停止中の人が自分で行う退会、再登録の防止 | 停止中は退会の申し込みを問い合わせで受け付ける | 別のメールアドレスでの再登録は元の仕様でも防げない。**停止中の人の削除の請求に応じる手順が必要** | M-06。運営者が本人確認のうえ、原則14日以内に処理する（11の7-3）。再登録は、悪用があれば再登録の防止を追加する |
| 退会の自動再開 | 途中で止まった退会は運営者が再開する | メールアドレスが残る時間が延びる。1日1回の確認で補う（24時間以内の目標はDB-25、未承認） | 手順書。確認を怠ると遅れることが懸念 |
| 管理者の閲覧の記録（DB-12の一部） | 前後10件を見ないため、記録の対象が減る | 措置・対応の記録は残る | 措置と通報の対応者・日時は残す（M-11） |

次の安全対策は**MVPから外さない**：RLSと権限の明示、住所・認証情報の分離、定員・重複のDBでの強制、送信関数に限った送信、ブロック、送信・操作の回数制限、通報と控え、利用停止と解除、退会時の個人情報の削除、管理者の多要素認証、Bot対策、規約等への個別の同意、18歳未満の募集作成の禁止、違反した募集の非表示。

| 対象 | 理由 |
|---|---|
| `public` の入口と `private` の処理本体を分ける構成 | 関数の数は増えるが、権限の誤りを防ぐ。公式も、公開するスキーマに権限の強い関数を置かないよう求めている（06の13章のS9） |
| ロックの順序（5-0） | 後から直すと、すべての関数に影響する |
| 募集と住所の分離、RLSと権限の明示 | 個人情報の保護に直結する |
| 申請の部分一意インデックスと行ロックでの定員管理 | 後から不整合を直せない |
| `seq`、`client_request_id` | 追加の負担が小さく、後から加えにくい |
| 通報の控え、措置の記録 | 対応の根拠になる |
| `users.id` に外部キーを置かない構成と段階を分けた退会 | 退会の仕組みの土台で、後から変えられない |
