# 03 要件定義書

表記ルールは [01_企画概要](01_企画概要.md) を参照。機能ごとの詳細は [04_機能一覧](04_機能一覧.md)、決定した詳細は [11_詳細仕様](11_詳細仕様.md) を参照。

## 1. システム概要

名古屋市内のバレーボールについて、主催者が募集を公開し、参加希望者が閲覧・質問・参加申請できるWebアプリ。主催者の承認によって参加が確定する。

## 2. サービスの目的【合意済み】

バレーボールをしたい参加者と、参加者を集めたい主催者をつなぐ。

## 3. 対象ユーザー【合意済み】

- 地域：名古屋市内
- 中心層：20代・30代の男女。年齢制限は設けず、他の年齢層も利用可能
- 経験：未経験者・初心者・経験者
- 参加形式：一人参加・友人同士の参加

## 4. 利用条件

| 条件 | 状態 |
|---|---|
| 募集の閲覧はログイン不要 | 【合意済み】 |
| 登録・ログインはメールアドレス＋パスワード方式。メール認証を行う | 【合意済み】 |
| 参加申請・承認・募集作成には利用者の識別が必要なため、ログインを必須とする | 【合意済み】の参加方式から導かれる前提 |
| チャットはログイン済みユーザーが利用できる | 【合意済み】 |
| ニックネームと経験レベルは必須 | 【合意済み】。初回ログインの直後に入力する（11のQ-40） |
| メール未認証ユーザーはログインできず、未ログインと同じ範囲を使える | 11のQ-40 |
| 登録時に「18歳以上」か「18歳未満（保護者の同意あり）」かを申告し、区分だけを記録する。生年月日は収集しない | 【合意済み】。18歳未満の制限と保護者の同意の確認方法は11の7-1。法的な条件は公開前に確認する（Q-30） |
| 利用規約・プライバシーポリシー・通報時のメッセージ確認への同意 | 登録時に個別に求め、版と日時を記録する（CND-09、11の7-2） |

- 管理者は一般ユーザーと同じ認証基盤を使い、管理者権限によって使える画面・操作を分ける【合意済み】。権限は運営者がDBの管理操作で付与する（11のQ-28）。
- 利用停止中のユーザーはメッセージを送信できない【合意済み】。そのほかの制限は11の4-2。

## 6. 機能要件

### 6-1. ユーザー登録・ログイン【合意済み】

- FR-01 メールアドレスとパスワードで登録・ログインできる
- FR-02 メール認証を行う
- FR-03 Googleログインは初期リリースでは実装しない
- FR-35 登録時に年齢の区分（18歳以上／18歳未満で保護者の同意あり）を申告する
- FR-47 登録時に、利用規約・プライバシーポリシー・通報時のメッセージ確認に同意する。改定で同意が必要な場合も、同意前に行える操作がある（11の7-2）

### 6-2. 募集の公開範囲【合意済み】

- FR-04 未ログインでも募集を閲覧できる（終了・中止した募集の詳細は、主催者と申請したことがある人だけ。11の2-1）
- FR-05 募集タイトル、開催日時、開催エリア、募集人数、参加費、主催者ニックネームを公開する
- FR-06 メールアドレス・電話番号は公開しない
- FR-07 詳細な開催場所・住所は参加承認されたユーザーだけに公開する
- FR-08 募集の閲覧と参加申請を区別する

終了日時・対象レベル・説明・持ち物・残り枠数も、未ログインユーザーに公開する（11のQ-24）。

### 6-3. 参加方式【合意済み】

- FR-09 ユーザーは募集に参加申請できる
- FR-10 申請時に主催者へ通知する
- FR-11 主催者は申請を承認または却下できる
- FR-12 承認された場合に参加確定となる
- FR-13 定員を超える参加申請を防止する
- FR-14 同一募集への参加申請の重複を防止する
- FR-33 主催者は、選択式の理由を指定して承認を取り消せる
- FR-34 承認の取り消し時に参加者へ通知する

定員の数え方【合意済み】：定員（募集人数）は募集する参加者の人数とし、主催者を含めない。承認済みの参加者だけを数え、承認待ちは数えない。**承認済み人数が定員を超えないこと**と、**満員の募集に申請できないこと**は必須とする。満員になっても承認待ちの申請は残し、空きが出れば承認できる。主催者は自分の募集に申請できない。

承認の取り消し【合意済み】：取り消しは、キャンセルや却下とは別の状態として記録する。枠が空き、参加者は詳細住所を見られなくなる。理由の選択肢は11のQ-19、通知はアプリ内（11のQ-11）。取り消された人は同じ募集に再申請できない（11のQ-14）。

操作の期限【合意済み】：参加申請・承認・却下・承認の取り消し・キャンセルは、開催開始時刻まで行える。開始後は変更できず、残った承認待ちは「受付終了」と表示する。時刻はDB側で判定する。締切・中止・日時変更の扱いは11のQ-16。

参加者の表示【合意済み】：参加者・申請者の一覧は主催者だけが閲覧できる。参加者同士には表示しない。募集が非表示の間は、主催者も閲覧できない（11の4-4）。

友人同士の参加【合意済み】：友人同士の場合も、各自が登録して1人ずつ申請する。友人同士であることは、チャット（FR-19）で主催者に伝える。

### 6-4. キャンセル【合意済み】

- FR-15 参加者はいつでもキャンセルできる
- FR-16 キャンセル時に主催者へ通知する
- FR-17 キャンセル時に残り枠数を更新する
- FR-18 キャンセル履歴を保存する

FR-15の「いつでも」は、開催開始時刻までであれば、直前を含めていつでもという意味とする【合意済み】。開始後の欠席の扱いを含め、無断欠席は初期リリースでは記録・表示しない（11のQ-26）。

### 6-5. チャット【合意済み】

- FR-19 ログイン済みユーザーは、参加申請前でも募集の主催者にメッセージを送信できる
- FR-20 募集の主催者と問い合わせユーザーの間でメッセージを送受信できる
- FR-21 ブロックした相手からのメッセージを拒否する
- FR-22 不適切なメッセージを通報できる
- FR-23 短時間の大量送信を制限する（具体的な数値は11のQ-10）

### 6-6. 安全対策【合意済み】

- FR-24 ユーザーを通報できる
- FR-25 ユーザーをブロックできる
- FR-26 募集を通報できる
- FR-27 管理者はユーザーを利用停止できる
- FR-32 管理者はユーザーの利用停止を解除できる

メッセージの報告はFR-22に含む。FR-21〜FR-27とFR-32はすべて初期リリースに含む。管理者の操作は「通報管理」と「利用者管理」の2画面に分ける。利用停止と解除の条件は11の4-2。

### 6-7. プロフィール【合意済み】

- FR-28 次の項目を管理できる

| 項目 | 必須・任意 |
|---|---|
| ニックネーム | 必須 |
| プロフィール画像 | 任意 |
| 自己紹介 | 任意 |
| 経験レベル | 必須 |
| 年代 | 任意 |
| 性別 | 任意 |
| 活動地域 | 任意 |
| バレーボール歴 | 任意 |
| ポジション | 任意 |

- FR-29 メールアドレス・電話番号を他のユーザーに公開しない

項目ごとの公開範囲【合意済み】：

| 項目 | 未ログイン | ログイン済み | 申請先の主催者 |
|---|:-:|:-:|:-:|
| ニックネーム | 主催者のものだけ | ○ | ○ |
| プロフィール画像・自己紹介・経験レベル・バレーボール歴・ポジション | × | ○ | ○ |
| 年代・性別・活動地域 | × | × | ○ |

- 本人は自分の全項目を閲覧できる
- 年代・性別・活動地域は、その主催者の募集に承認待ちまたは承認済みの申請がある人の分だけ、募集の終了日時まで主催者が閲覧できる。中止・非表示になった場合は閲覧できない
- プロフィール画像は非公開で保存し、ログイン済みユーザーだけに表示する
- 管理者の閲覧範囲は11のQ-28、ブロックした場合の影響はQ-20、メール未認証ユーザーの扱いはQ-40

選択肢や文字数は11のQ-19。電話番号は管理項目に含まれていないため、**収集しない**設計とする【提案】。

### 6-8. 募集

- FR-30 ログイン済みユーザーは募集を作成できる【合意済み】（サービスの目的から必須）。18歳未満は作成できない（11の7-1）
- FR-31 募集を検索できる【合意済み】。検索条件は11のQ-23
- FR-38 主催者は開催開始前に、募集の編集・締切・中止ができる【合意済み】。詳細は11のQ-16
- FR-39 主催者は自分が主催した募集の一覧を確認できる【合意済み】

### 6-9. 退会【合意済み】

- FR-36 ユーザーは退会できる
- FR-37 退会時に、プロフィール・画像・メールアドレス・主催した募集の住所などの個人情報をすぐに削除し、メッセージや参加の記録は「退会したユーザー」として匿名で残す
- 開催開始前の募集がある主催者は、中止するか開催が始まるまで退会できない（利用停止中の場合は、募集を自動で中止にして退会できる）
- 開催開始前の参加は自動でキャンセルし、主催者へ通知する。承認待ちの申請は取り下げとする
- 通報・利用停止の記録は退会後も残す。期間は11の4-8
- 退会の前にパスワードの再入力を求める。途中で止まった退会は24時間以内に完了させる（11の3-4）
- 退会後の再登録、利用停止中の退会は11のQ-52

### 6-10. そのほかの機能【合意済み】

2026-11-25に、ユーザーから判断を一任されて決めた機能。詳細は11。

- FR-40 申請者は、開催開始時刻まで承認待ちの申請を取り下げられる
- FR-41 承認・却下・募集の重要な変更・中止・非表示とその取り消しを、関係するユーザーへアプリ内で通知する
- FR-42 主催者は、自分の募集の申請者・参加者に対して会話を開始できる
- FR-43 ユーザーは、ブロックした相手を確認し、ブロックを解除できる
- FR-44 管理者は、不適切な募集・メッセージを非表示にし（取り消しもできる）、プロフィール画像を削除できる
- FR-45 パスワードの再設定と、認証メールの再送ができる
- FR-46 募集の作成・通知をともなう編集・申請・通報・ブロックの回数を制限し、登録などをBotから保護する

## 7. 非機能要件

数値目標は11の7-5（Q-39）。

| 分類 | 方針【提案】 |
|---|---|
| 使いやすさ | 初めての人でも迷わず閲覧・申請できる画面にする |
| 性能 | 一覧はページ分割し、必要なデータだけを取得する |
| 整合性 | 定員・重複はデータベース側で保証し、同時操作でも崩れないようにする |
| 可用性 | 無料プランの一時停止・上限を把握したうえで運用する（[05](05_技術構成・開発環境.md)） |
| 保守性 | TypeScriptで型を付け、DB変更はマイグレーションで管理する |
| 拡張性 | 対象地域・通知手段・ログイン方式を後から追加しやすくする |
| アクセシビリティ | キーボード操作、ラベル、十分なコントラストに配慮する |
| バックアップ | Supabase無料プランには自動バックアップがないため、手動でバックアップする（11のQ-05） |
| 費用 | 初期費用はできるだけ無料【合意済み】 |

## 8. セキュリティ要件

| No. | 要件 |
|---|---|
| SR-01 | 通信はHTTPSで行う |
| SR-02 | パスワードは認証基盤（推奨構成ではSupabase Auth）に任せ、アプリのテーブルに保存しない |
| SR-03 | 公開スキーマの全テーブルでRLSを有効にし、許可した操作だけを通す |
| SR-04 | 画面の表示制御だけに頼らず、データベース側でアクセスを拒否する |
| SR-05 | 詳細住所は公開情報と別テーブルに分け、主催者と承認済みユーザーだけが取得できる |
| SR-06 | 定員・重複・ブロック・送信回数の制限はサーバー側で強制する |
| SR-07 | 管理者権限と利用停止状態を、一般ユーザーが書き換えられないようにする |
| SR-08 | RLSを迂回できるシークレットキーをフロントエンドやGitHubに置かない |
| SR-09 | 利用者の入力はエスケープして表示し、XSSを防ぐ |
| SR-10 | 画像の形式と容量を制限し、本人の領域だけに保存を許可する |
| SR-11 | ログや通知に詳細住所・メールアドレスなどを不必要に含めない |

## 9. 個人情報の取り扱い

| 情報 | 取得 | 公開範囲 |
|---|---|---|
| メールアドレス | 登録に必要 | 他のユーザーに公開しない【合意済み】 |
| パスワード | 登録に必要 | 公開しない |
| 電話番号 | 収集しない【提案】 | 公開しない【合意済み】 |
| 年齢の区分 | 登録時に申告 | 本人のみ |
| ニックネーム | 必須 | 主催者のものは未ログインにも公開、それ以外はログイン済みに公開【合意済み】 |
| プロフィール（ニックネーム以外） | 経験レベル必須、ほか任意 | 年代・性別・活動地域は本人と申請先の主催者（終了日時まで）のみ。ほかはログイン済みに公開【合意済み】（6-7） |
| 詳細な開催場所・住所 | 募集作成時 | 主催者と承認済みユーザーのみ【合意済み】 |
| メッセージ | チャット利用時 | 会話の当事者。通報された場合、管理者は対象のメッセージと、その前後10件ずつ（同じ会話内）に限定し、通報への対応中だけ閲覧できる【合意済み】（11のQ-28） |
| 通報・ブロック情報 | 操作時 | 通報は管理者のみ（通報者には受付完了だけを示す、11の4-3）、ブロックは本人のみ【提案】 |
| キャンセル履歴 | キャンセル時 | 本人と、その募集の主催者 |

- 退会時の削除は6-9【合意済み】。通報・利用停止の記録の保存期間は11の4-8
- メッセージの本文に書かれた個人情報は退会後も残り得るため、入力時の注意とプライバシーポリシーで扱う（11の7-3）
- プライバシーポリシーに書く内容は11の7-3。文章は公開前に作成し、確認を受ける
- 個人情報保護法、電気通信事業法、出会い系サイト規制法との関係は、公開前に専門家や所管官庁への確認が必要（Q-33〜Q-35。方針は11の7-4）

## 12. 将来的な拡張方針【提案】

- ログイン方式・通知手段・対象地域は、後から追加できるように設定やコードを分離する
- 利用状況と意見を見て優先順位を決める
- 無料枠を超える前に、有料化・構成変更の判断を行う（Q-05）
